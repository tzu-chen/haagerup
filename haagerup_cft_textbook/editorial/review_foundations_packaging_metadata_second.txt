Two remaining concrete integrity gaps
------------------------------------
1. Fresh path discovery can omit a file that already passed a gate.

   At lines 86-98 the package list is reconstructed by globbing. Suppose
   a chapter is validated/pinned at 42-44 and then removed before its
   directory is globbed. It will not appear in paths, so there is no
   later checked_bytes call for it and the ZIP can succeed without a
   source listed in its included build record. The same applies to a
   checker or JSON record, including the supposedly required snapshot,
   if deleted after its validation and before discovery.

   Minimal repair: seed paths with the initially validated required
   files, then union the discovered extras. Retain their logical names;
   the separately delivered PDF is the one deliberate exclusion from
   ZIP payloads. The existing is_file and payload checks then reject
   deletion. This does not require rescanning external scientific files.

2. The generated manifest is not pinned to the bytes just constructed.

   Line 118 writes serialized manifest content, but line 131 is the
   first checked_bytes call for manifest.json. Its special case at 132
   also skips the ordinary expected-payload comparison. If the manifest
   is edited between creation and ZIP read, the modified content becomes
   its first accepted identity and can enter the ZIP even though the
   source checks used the original in-memory manifest dictionary.

   Minimal repair: serialize to one bytes value, establish its expected
   hash/length from that value BEFORE any reread, and write those exact
   bytes. The existing checked_bytes call then catches any later edit.
   Alternatively use the in-memory payload for the ZIP and also verify
   that the delivered standalone manifest still contains those bytes.
   There is no need for a self-referential manifest hash entry.
